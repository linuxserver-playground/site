// Contribute

We need people more than money

LinuxServer.io has been run by volunteers since the start, and today a handful of people look after 198 images, their mods and everything that builds them. What keeps it going is not donations. It is people in chairs: fixing the image they run, writing the mod they need, bringing the app they want.

You do not need to understand how a decade of infrastructure fits together first. Bring an AI coding agent; we give it everything it needs to know.

Start in three commands Pick a way in

// The harness

An agent that already knows the org

The harness (opens in a new tab) is a repository you clone and start your agent in. It holds a map of the whole system, a playbook for every kind of request, our rules and the tools to test locally. Then you ask in plain words.

  • Reads the whole org for you: every repo, the conventions, live builds, issues and pull requests.
  • Works out whether you are on the team or contributing from outside, and follows the right path.
  • Builds and runs the image in your own Docker before anyone calls a change done.
  • Drafts the issue, pull request or review. You read every word before it is filed.

You need git, the GitHub CLI signed in, jq, curl and Docker, plus an agent that reads AGENTS.md (Claude Code, or any other). The full guide covers the rest.

~/harness
$ gh repo clone linuxserver-playground/harness && cd harness$ ./harness doctor$ ./harness core$ claude   # or any agent that reads AGENTS.md

// Ways in

Start with what you already use

The best first contribution scratches your own itch. Every one of these works with an agent, or by hand with the guide.

  • Fix an image you use

    Something broken, missing or out of date in an image you run. The agent reproduces it in your Docker, makes the smallest fix and drafts the pull request.

    › My <image> container <what goes wrong>. Reproduce it, fix it and draft the PR.
    Read the guide

  • Make the mod you need

    A package, a driver or a tool only some users want belongs in a mod, not the image. Mods are a Dockerfile and a few scripts, and the agent tests them for you.

    › Make a mod that installs yt-dlp into any image, and test it.
    Read the guide

  • Bring an app you want

    New applications start in LinuxServer Labs. Build and run your app's image locally from the Labs template, or let the agent check the bar and fill in the proposal form from real data, for you to read before it is filed.

    › I'd like <app> in LinuxServer Labs. Check it meets the bar and draft the proposal.
    Read the guide on Labs (opens in a new tab)

  • Improve the docs

    Every docs page is Markdown in the site repository. If a page confused you, you are the right person to fix it.

    › The <page> docs page <what confused you>. Fix it and draft the PR.
    Read the guide

  • Explain a red build or an issue

    Half of maintenance is working out why something broke. Ask the agent, check what it found, and post the explanation where it helps.

    › Explain the newest red build on the fleet board. Is it us, upstream or a network flake?
    Read the guide

  • Review a pull request

    Build and run someone else's change locally and compare it with the released image. A second pair of eyes is what keeps a small team moving.

    › Review PR 6 on docker-heimdall. Build it, run it and compare it with the released image.
    Read the guide

// Right now

Where help is needed

All of it is public. Ask your agent to rank it, or just look.

  • Open issuesBugs and requests across every repository, live from the control plane.
  • Pull requestsChanges waiting for a build, a review or a second opinion.
  • The fleet boardEvery live branch and its last build. A red one is a good first fix.
  • Labs images in reviewNew apps a team member has tried and put forward in Labs. Pull one, run it and say how it went.(opens in a new tab)

// After you open it

What happens to your pull request

  1. 1A maintainer approves the runGitHub holds builds from outside accounts until someone on the team clicks "Approve and run". Waiting here is normal.
  2. 2Both architectures build and testWith no secrets and a read-only token. One comment on your pull request reports the tests, screenshots and package changes.
  3. 3Someone reviews itOften with an agent of their own, building your change locally. Questions come to you, so answer in your own words.
  4. 4It shipsMerging releases the image. Its build page appears on this site within minutes, and your change is in the release notes.

// Ground rules

Agents draft, people decide

  • AI is welcomeSay which tool you used and for what, in the pull request description. Undisclosed AI-generated pull requests are closed.
  • A person is accountableYou open the pull request, you have read every line and run the result, and you can answer questions about it. Agents draft; people file.
  • Small and finishedOne focused change per pull request, tested before you open it. Every push rebuilds both architectures.

The full rules are in Contributing an image.

LinuxServer Labs

A place for the software you want to see

New and smaller self-hosted apps start in Labs: the same pipeline and base images as the main fleet, with a lower bar for the software. The guide on the Labs site covers what qualifies and why, building and running your app's image locally from the Labs template, proposing it with an AI agent or by hand, and what happens after. The good, popular and maintained ones graduate to the main fleet.
