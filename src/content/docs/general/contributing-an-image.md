This page is for anyone opening a pull request against a `docker-<name>` repository in `linuxserver-playground`. It summarises the [org `CONTRIBUTING.md`](https://github.com/linuxserver-playground/.github/blob/main/CONTRIBUTING.md) and [`CONVENTIONS.md`](https://github.com/linuxserver-playground/builder/blob/main/CONVENTIONS.md) §2 and §8, which are the authoritative texts. If you are used to the `linuxserver` repositories: there is no Jenkinsfile, no `jenkins-vars.yml`, no `readme-vars.yml`, no per-repo trigger workflows and no templates repository to update. There is `image.yml`, and a tool that checks it.

## Decide where the change belongs

Every package, variable and init step we add is maintained, rebuilt weekly and supported forever, for every user. Work down this list and stop at the first match:

1. **A bug or feature in the application itself**: upstream, with the app's developers. We do not patch or work around upstream behaviour in the image.
2. **An unsupported or reasonable-endeavours environment** (Podman, Kubernetes, LXC, NFS `/config`, custom entrypoints; see the [support policy](/docs/misc/support-policy/)): no image logic will be added for it. The [guides](/docs/general/platform-stores/) exist instead.
3. **Only your setup needs it**: a private [custom script or service](/docs/general/container-customization/). No PR needed.
4. **A subset of users would use it** (an extra package, driver, plugin, integration): a [Docker Mod](https://github.com/linuxserver-playground/docker-mods). Check whether one exists first.
5. **The image is broken, or the large majority of its users benefit**: a PR to the image repository.

"It is only a few lines" is not a reason. If in doubt, ask in [Discussions](https://github.com/orgs/linuxserver-playground/discussions) or on [Discord](https://linuxserver.io/discord) first. Typo and wording-only fixes: open an issue, not a PR.

## The repository

```
Dockerfile              amd64, FROM ghcr.io/linuxserver/baseimage-<base>:<tag>
Dockerfile.aarch64      arm64, identical except the base tag
root/                   copied to / in the image; s6-overlay v3 units under root/etc/s6-overlay/s6-rc.d
image.yml               the manifest. The only hand-edited metadata file.
package_versions.txt    written by the build on the live branch, never hand-edited
README.md               generated by `builder render`, never hand-edited
AGENTS.md               generated by `builder render`, never hand-edited
LICENSE                 GPL-3.0, generated
.github/workflows/build.yml   ~20 lines, generated, calls workflows/image-build.yml@v1
```

You edit three things: the two Dockerfiles (any change goes in both; packages one per line, alphabetical), `root/` (s6 scripts start with `#!/usr/bin/with-contenv bash` and `# shellcheck shell=bash`, and must be executable) and `image.yml`. Everything else is generated or written by CI, and a pull request that touches a generated file fails `builder check`. Do not add compose files, Makefiles, test suites, linter configs, pre-commit hooks, extra workflows or a `CHANGELOG.md`.

Some repositories have more than one live branch (`develop`, `nightly`, ...), each with its own `image.yml`. Target the branch the change applies to; never merge one into another.

### `image.yml`

The manifest is validated against [`image.schema.json`](https://github.com/linuxserver-playground/builder/blob/main/schemas/image.schema.json). Its sections, briefly:

| Section | What it drives |
| --- | --- |
| `name`, `summary`, `upstream` | The title and blurb everywhere; where the version and release notes come from (`upstream.version` is typed: `github_release`, `json` + `jq`, `alpine_apk`, `pip`, `npm`, `command`, ...); `sponsor` links. |
| `release` | `branch`, the `tag` it publishes, `channel`, and the list of `tags` with their descriptions for the Version Tags table. |
| `build` | `base`, `version_arg` (the Dockerfile `ARG` the resolved version is passed as), `platforms`. |
| `test` | `web.port` and `path` for the CI browser probe, `startup_timeout`, `enabled`. |
| `runtime` | `ports`, `volumes`, `env`, `devices`, `cap_add`, `security_opt`, `network`, `privileged`, `custom`; each entry has a `description` and may be `optional`. This is the parameter table, the compose and run snippets, the store templates, the Kubernetes manifest and the quadlet. `readonly.supported` and `nonroot.supported` record what has been tested. |
| `docs` | `categories`, `logo`, `setup` (the Application Setup section, Markdown), `optional_parameters`, `notices` (`media`, ...). |
| `proxy` | What SWAG needs: `port`, `subdomain`, `subfolder`, `api_locations`, `websocket`. |
| `publish` | Per-platform switches (`stores.unraid: false`, `kubernetes.enabled`, `kubernetes.workload`, `kubernetes.persistence`, `quadlet`), Unraid `requirement` and `webui`. |
| `deprecation` | `status` and `message`. |
| `changelog` | Newest first. Every Dockerfile or `root/` change adds an entry. |

User-facing text lives here, not in `README.md`. If the docs page is wrong, fix `image.yml`.

## Validate with `builder check` and `builder render`

The `builder` tool ships as a container. Run it from the root of the image repository:

```bash
# validate image.yml, report generated files that drifted, lint s6 scripts and the changelog
docker run --rm -v "$PWD":/repo ghcr.io/linuxserver-playground/builder:latest check

# rewrite README.md, AGENTS.md, LICENSE and .github/workflows/build.yml from image.yml
docker run --rm -v "$PWD":/repo --user "$(id -u):$(id -g)" ghcr.io/linuxserver-playground/builder:latest render
```

`check` exits 1 and prints the file, the field (a JSON path into `image.yml`) and the line. It also verifies that both Dockerfiles agree apart from `FROM`, that every s6 `run`, `finish` and `check` is executable with the right shebang, that the changelog is newest first, that `release.branch` matches the branch you are on, and that nothing looks like a credential. The PR build runs the same check, so run it before you push. `pip install -e .` in a checkout of the builder repository gives you a bare `builder check` and `builder render` instead.

If you changed `image.yml`, run `render` and commit the regenerated files together with the manifest. On a live branch the workflow would do it for you as `Update generated files [skip ci]`; in a pull request it is your job, because `check` fails on drift.

## Update the changelog

If you modify a Dockerfile or anything under `root/`, add an entry at the **top** of `changelog:` in `image.yml`, one short factual sentence:

```yaml
changelog:
- date: '2026-10-24'
  text: Add libfoo to fix thumbnail generation.
```

Documentation-only changes to `image.yml` do not need an entry.

## Test it for real

```bash
git clone https://github.com/linuxserver-playground/docker-<name>.git
cd docker-<name>
docker build --no-cache --pull -t <name>:test .
docker run --rm -e PUID=1000 -e PGID=1000 -e TZ=Etc/UTC -v "$PWD/testconfig:/config" -p <port>:<port> <name>:test
```

Confirm `[ls.io-init] done.` appears in the log, the app comes up, and it survives a restart against an **existing** `/config`, not just a fresh one. The arm64 image can be built on x86-64 after `docker run --rm --privileged ghcr.io/linuxserver/qemu-static --reset`, with `docker build -f Dockerfile.aarch64 --platform linux/arm64 ...`.

Once the PR is open, GitHub Actions builds and tests both architectures and publishes `ghcr.io/linuxserver-playground/untrusted-pr/<name>:pr-<number>-<sha7>` for reviewers (fork PRs upload the image as a workflow artifact instead). A single comment on the PR is updated with the result, and the run is listed under [pull requests](/fleet/pulls/). PR images are deleted when the PR closes and are never for production use.

## Pull request rules

* **Disclose AI use.** AI-assisted contributions are welcome and must be disclosed in the PR description: which tool, and what it was used for. Undisclosed AI-generated PRs will be closed.
* **A human is accountable.** The person opening the PR must have read and understood every line, built and run the image, and be able to answer review questions in their own words. Fully autonomous agents must not open PRs or issues.
* **One focused change per PR.** The smallest diff that fixes the problem. No drive-by refactors, reformatting, comment rewording or dependency shuffling.
* **Finish before you open.** Every push to an open PR starts a full build and test on both architectures. No drafts iterated in public with a stream of fixup commits.
* **Fill in the PR template honestly**: description, benefit to the wider userbase, how it was tested (real commands, real output) and links. If the PR addresses an issue, include `closes #<number>`.
* **Commit subjects are short imperative sentences** (`Add krb5-libs for postgresql support`). No conventional-commit prefixes, no emoji, no trailers of any kind.
* A PR that touched generated files, or whose manifest does not validate, fails `builder check` with the file, field and line.
* A PR is a proposal; it may be declined even if it works. The most common reason is the list at the top of this page.

## Contributing to the infrastructure

The builder, workflows, ci, hub, control and site repositories each have an `AGENTS.md` with the same headings (Purpose, Layout, What you may edit, How to validate, Contracts, Pull request rules) that says what is specific to them. The same PR rules apply. For these pages, see [CONTRIBUTING.md in the site repository](https://github.com/linuxserver-playground/site/blob/main/CONTRIBUTING.md); remember that the image pages are generated from `image.yml` and cannot be edited there.
